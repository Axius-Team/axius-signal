## Authentication

Project Key Authentication

Axius Signal uses a DSN-style project key as the sole authentication credential when operating in connected mode. This document explains how authentication works and how to manage your project key.

How It Works

The project key is a single opaque string generated by the Axius Pro dashboard. It follows the format `axius_pk_<random>` and is pasted into the SDK configuration at initialization time.

```
import { Signal } from 'axius-signal';

const signal = Signal.init({
  projectKey: 'axius_pk_your_project_key',
  environment: 'production',
});
```

The SDK sends the key as a Bearer token in the Authorization header of every request to the ingestion service:

```
Authorization: Bearer <project_key>
```

Key Properties

- The project key identifies and authorizes a project only. It does not encode plan or tier information.
- Plan limits and entitlements are learned separately by querying the ingestion service config endpoint, which returns the current plan based on the authenticated project.
- The key is stateless with respect to plan information. This means plan changes happen server-side without requiring a key update.
- If no project key is configured, the SDK never makes a network call. The capture and local-sink paths work identically in local-only mode.

Security Model

- The SDK never rotates, refreshes, or modifies the key. Rotation and revocation are entirely server-side operations in the Axius Pro dashboard.
- If a key is revoked, the next SDK request receives a 401 response. The transport layer handles this by permanently dropping the queued events for that project and emitting a warning through the local sink.
- The project key is a static secret in your application configuration. Treat it as sensitive information. Use environment variables or a secret manager to store it.
- Do not commit the project key to source control.

Best Practices

1. Store the project key in an environment variable or secret manager, never in source code.
2. Rotate the key from the Axius Pro dashboard if you suspect it has been leaked.
3. Use different project keys for development, staging, and production environments.
4. Revocation is immediate. The dashboard marks the key as revoked, and the SDK stops sending telemetry on the next request.

Why Not OAuth or Other Methods

The project key approach was chosen over alternatives for these reasons:

- Username and password authentication would conflate user identity with project authorization and does not support multi-project setups.
- OAuth2 client credentials add unnecessary complexity for a use case that only requires a long-lived static secret.
- API keys in query parameters expose the key in server logs and URL references.
- mTLS with client certificates adds operational overhead that is inappropriate for a developer-facing library.
- An open ingestion endpoint with no authentication would allow anyone who discovers a project ID to inject telemetry.

The project key model keeps the developer experience simple: one opaque string, copied from dashboard to configuration. No token refresh, no expiry, no scopes.
